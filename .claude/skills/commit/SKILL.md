# /commit — יצירת commit ודחיפה

בדקו את מצב הריפו, הרכיבו הודעת commit ברורה באנגלית, צרו commit ודחפו אותו ל-remote.

**שימוש:** `/commit`

## הוראות

### 1. בדיקת מצב הריפו

הריצו במקביל:

```bash
git status
git diff
git diff --staged
git log --oneline -10
git status -sb
```

בדקו גם אם הענף עוקב אחרי remote ואם יש הבדל בין המקומי לרחוק (`ahead`/`behind` בפלט של `git status -sb`).

אם אין שום שינוי (לא ב-staged, לא ב-unstaged, בלי untracked רלוונטי) — ספרו למשתמשת שאין מה לקמט ועצרו.

### 2. סינון לפני staging

עברו על פלט `git status`. **לפני** הוספת קבצים:

- זהו קבצים שנראים כמו סוד/קרדנשלס (`.env`, `*credentials*`, מפתחות API) — אם יש, הזהירו את המשתמשת ואל תוסיפו אותם בלי אישור מפורש.
- זהו קבצים שנראים כמו scratch/זמניים מקומיים (למשל סקריפטים זמניים בשורש הריפו) — אם לא ברור אם הם אמורים להיכנס לקומיט, שאלו את המשתמשת במקום להניח.
- אל תשתמשו ב-`git add -A` או `git add .`. הוסיפו קבצים ספציפיים בשמם, כדי לא לגרור בטעות קבצים לא-קשורים.

### 3. הרכבת הודעת הקומיט

הודעות הקומיט בריפו הזה **באנגלית**, שורת סיכום קצרה בלשון ציווי (למשל `Add`, `Fix`, `Update`, לא `Added`/`Fixed`), ולפעמים גוף עם פירוט. הביטו ב-`git log` שהרצתם כדי להתאים לסגנון הקיים.

- אם השינויים קשורים בבירור ל-issue ספציפי (מהשיחה, מהענף, או מהקוד עצמו) — אפשר לציין את זה בגוף ההודעה (`Refs #<number>`), אבל אל תניחו קשר ל-issue אם הוא לא ברור — שאלו אם יש ספק.
- אם יש כמה שינויים לא-קשורים לגמרי בסטטוס (לדוגמה תיקון UI ולצידו refactor בתחום אחר) — ציינו זאת למשתמשת ושאלו אם לפצל לכמה commits נפרדים או לקבץ לאחד.
- ההודעה מסכמת **למה** השינוי נעשה, לא רק **מה** השתנה — הקוד עצמו כבר מראה מה השתנה.

### 4. הצגה ואישור

הציגו למשתמשת:
- אילו קבצים ייכנסו לקומיט
- טיוטת הודעת הקומיט
- שהפעולה תסתיים ב-push לענף המרוחק (ציינו את שם הענף)

חכו לאישור או לתיקון לפני שמריצים בפועל.

### 5. ביצוע ה-commit

```bash
git add <קבצים ספציפיים>
git commit -m "$(cat <<'EOF'
<כותרת קצרה בלשון ציווי>

<גוף אופציונלי, אם נדרש הסבר נוסף>

Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>
EOF
)"
git status
```

### 6. דחיפה ל-remote

```bash
git push
```

- אם הענף לא עוקב אחרי remote (push ראשון), השתמשו ב-`git push -u origin <branch>`.
- אם ה-push נדחה כי הענף המרוחק התקדם (non-fast-forward) — **אל תעשו force push**. עצרו, ספרו למשתמשת מה קרה, והציעו `git pull --rebase` או בדיקה ידנית שלה לפני שממשיכים.
- ודאו אחרי ה-push עם `git status` שהענף המקומי מסונכרן עם המרוחק.

### 7. גבולות

- **בלי force push** — לעולם לא `--force`/`--force-with-lease` בלי בקשה מפורשת של המשתמשת לפעולה הזו הספציפית.
- **בלי `--no-verify` / `--no-gpg-sign`** — אם pre-commit hook נכשל, תקנו את הבעיה האמיתית והריצו commit חדש; אל תעקפו את ה-hook.
- **בלי `--amend`** — תמיד commit חדש, אלא אם המשתמשת מבקשת amend במפורש.
- אם `git push` דורש אימות/הרשאות שלא קיימות בסביבה, דווחו למשתמשת מה חסר ועצרו — אל תנסו לעקוף.
