# /new-issue — פתיחת issue חדש

ראיינו את המשתמשת על בעיה או רעיון, קראו את הקוד הרלוונטי, וצרו issue מובנה וברור ב-GitHub.

**שימוש:**
- `/new-issue` — התחלת הראיון (או המשך שיחה שכבר קיימת)
- `/new-issue <מספר>` — טעינת issue קיים, קריאת קוד רלוונטי, ודיון על הספק שלו

## הוראות

### 0. טעינת הקשר וחקירת הקוד

אם עוד לא נקרא `CONTRIBUTING.md` בשיחה הזו — קראו אותו עכשיו.

**זהו מיד** את התחום שהבעיה/הרעיון נוגעים אליו (מהודעת המשתמשת, מהשיחה עד כה, או מתוך ה-issue הנטען). לפני ששואלים משהו — בנו הבנה עמוקה של האזור הרלוונטי:

1. **בדקו את מבנה הפרויקט** ב-`CONTRIBUTING.md` כדי לדעת איזו תיקייה רלוונטית (`js/pages/`, `js/utils/`, `js/components/`, `js/auth/`, `js/onboarding/`, `js/quiz/`, `js/rating/`, `css/`).
2. **חקרו את הקוד עצמו** — Grep/Glob/Read ישירות, או Agent מסוג Explore לחיפוש רחב יותר. הקוד הוא מקור האמת, לא רק התיאור למעלה.
3. **הבינו מה קיים היום** — לפני ששואלים "איפה כדאי לשים את זה?" תדעו בעצמכם מה יש כבר במסך/רכיב הרלוונטי ותשאלו שאלה ממוקדת יותר.

המטרה: השאלה הראשונה שלכם צריכה להראות שכבר מבינים את המערכת. במקום "איפה זה צריך להיות?" — "זה צריך לשבת מתחת לכרטיס הציונים בדף הבית, או בלשונית נפרדת בהגדרות?".

### 1. זיהוי מצב והתמצאות

**אם הופעל עם מספר issue** (למשל `/new-issue 12`):

1. הביאו את ה-issue והתגובות שלו:
   ```bash
   gh issue view 12 --comments
   ```
2. זהו את התחום מתוך תוכן ה-issue וקראו את הקוד הרלוונמי — במקביל להבאת ה-issue.
3. סכמו ב-2-3 משפטים את ההבנה שלכם ומה קראתם. הזמינו לדיון: "על מה תרצי לעבוד?"
4. אל תשאלו על עדיפות ואל תזוזו לכיוון יצירה אלא אם המשתמשת מבקשת — המצב הזה מיועד לדיון על הספק, לא לקליטת רעיון חדש.

**אם הופעל בלי ארגומנטים:**

בדקו אם השיחה הנוכחית כבר מכילה הקשר משמעותי על בעיה או רעיון. אם כן — המשיכו את החוט: קראו קוד רלוונטי מיד, סכמו את ההבנה, ושאלו רק את מה שעדיין לא ברור.

אם אין הקשר קודם, פתחו בשאלה פשוטה:

> "מה עובר לך בראש? ספרי לי על הבעיה או הרעיון."

ואז נהלו **שיחה טבעית**. אל תשתמשו ב-AskUserQuestion לדיון המרכזי — פשוט שוחחו. התפקיד שלכם הוא להקשיב, לשאול שאלות הבהרה בטקסט חופשי, ולבנות בהדרגה תמונה ברורה.

**בכל המצבים**, ככל שהשיחה מתפתחת:

- **חקרו לפני ששואלים** — קראו את הקוד עצמו (לא רק את התיאור למעלה) כדי שהשאלות שלכם יתייחסו לפרטים אמיתיים במערכת. לעולם אל תשאלו שאלה שקריאת הקוד הייתה עונה עליה.
- **שאלות ממוקדות** — התבססו על מה שמצאתם: "ב-`js/utils/gradeCalc.js` יש כבר חישוב ממוצע משוקלל — הפיצ'ר החדש אמור להשתמש בו או לבנות לוגיקה נפרדת?", לא "איך לחשב את זה?".
- **שקפו בחזרה** — סכמו במשפט-שניים מה אתם חושבים שה-issue הוא, ותנו למשתמשת לתקן. כך מתכנסים לתיאור ברור.
- **בלי חקירה מיותרת** — אם המשתמשת נתנה הסבר ברור ומלא מההתחלה, אל תשאלו שאלות מיותרות. המשיכו הלאה.

### 2. שאלה על עדיפות

ברגע שההבנה מספקת לכתיבה, השתמשו ב-AskUserQuestion עבור **הדבר היחיד שדורש תשובה מובנית** — עדיפות:

- **Blocking** — "משהו שבור/חוסם, לתקן עכשיו."
- **VNH** — "Very Nice to Have — שיפור משמעותי, בקרוב."
- **Dream** — "רעיון נחמד, לא דחוף. Backlog."

### 3. כתיבת ה-issue

**כותרת:**
- קצרה וממוקדת
- לשון ציווי ("הוסיפי X" ולא "הוספת X")
- ספציפית לגבי מה ה-issue מספק

**מבנה התיאור:**

```markdown
## תקציר
1-3 משפטים שמסבירים על מה ה-issue ולמה זה חשוב.

## פרטים
- נקודות שמכסות scope, כיוון גישה, שיקולים מרכזיים
- אזכור רכיבים ספציפיים בשם (למשל "מסך `js/pages/grades.js`", "פונקציית `calcWeightedAverage`")
- הקשר רלוונטי מתשובות המשתמשת

## קריטריוני קבלה
- [ ] תנאים קונקרטיים וניתנים לבדיקה שמגדירים "גמור"
- [ ] כל קריטריון צריך להיות ניתן לבדיקה
```

תיאורים תמציתיים וממוקדי-פעולה. בלי ריפוד במשפטים כלליים.

### 4. הצגה ואישור

הציגו למשתמשת את הכותרת, התיאור והתווית המוצעים לפני היצירה. המתינו לאישור.

### 5. יצירת ה-issue

```bash
# ודאו שהתוויות קיימות
gh label create "<label>" --description "" --color "c5def5" 2>/dev/null || true
gh label create "Claude" --description "Issue touched by Claude" --color "c5def5" 2>/dev/null || true

# יצירת ה-issue עם תווית עדיפות + Claude
gh issue create --title "<title>" --label "<label>" --label "Claude" --body "$(cat <<'EOF'
<description>
EOF
)"
```

### 6. דיווח

אשרו את היצירה עם מספר ה-issue והקישור. הפלט של `gh issue create` כולל את ה-URL — הדפיסו אותו ישירות.
