# /plan-issue — תכנון מעמיק

חידוד איטרטיבי של תוכנית מימוש דרך כמה סבבי תכנון. בכל סבב Plan subagent חדש בוחן את התוכנית הנוכחית — מוצא פערים, חוסר עקביות, שלבים חסרים — ומעמיק כל פעם. מתייעצים עם המשתמשת בין הסבבים כדי לתקן כיוון. כשהתוכנית יציבה, מפרסמים אותה. אם היא גדולה מדי, מפצלים ל-issues בנים.

**מניח שקיים issue כתוב היטב.** בלי הבהרה מקדימה — מתכננים מיד.

## דרישות מקדימות

קראו את `CONTRIBUTING.md` (דלגו אם כבר נקרא בשיחה הזו).

## הוראות

### 1. הבאת ה-issue

מספר ה-issue: **$ARGUMENTS**

אם ריק או לא מספר, עצרו ושאלו: "איזה issue? שימוש: `/plan-issue 42`"

```bash
gh issue view $ARGUMENTS
gh issue view $ARGUMENTS --comments
```

### 2. טעינת הקשר

זהו אילו תיקיות/קבצים ה-issue נוגע בהם, לפי מבנה הפרויקט המתואר ב-`CONTRIBUTING.md` (`js/pages/`, `js/utils/`, `js/components/`, `js/auth/`, `js/onboarding/`, `js/quiz/`, `js/rating/`, `js/data/`, `css/`). קראו את הקבצים הקיימים הרלוונטיים ישירות — StudyTop קטן מספיק שאין צורך בסקילים נפרדים לפי תחום, פשוט לחקור את הקוד עצמו (Grep/Glob/Read, או Agent מסוג Explore לחיפוש רחב).

הבינו את המצב הנוכחי לפני שמתכננים.

תייגו את ה-issue:
```bash
gh issue edit $ARGUMENTS --add-label "Planning"
```

### 3. הרצת Plan subagent ראשון

**אל** תדונו עם המשתמשת קודם. מיד הריצו Plan subagent.

תנו ל-subagent:
- את גוף ה-issue המלא וכל התגובות
- אילו קבצים/תיקיות מעורבים, לפי מה שמצאתם
- דפוסי קוד וקבצים רלוונטיים שמצאתם בזמן טעינת ההקשר
- הנחיה להפיק תוכנית מימוש מלאה בפורמט שלמטה

ה-subagent צריך להפיק תוכנית ברמת פירוט גבוהה — נתיבי קבצים מדויקים, דפוסי קוד, תלויות סדר, ואיך לבדוק שזה עובד.

**פורמט התוכנית שה-subagent חייב לעקוב אחריו:**

```
## תוכנית מימוש

### תקציר
<1-2 משפטים>

### שלבים
1. **<נתיב קובץ מדויק>** — מה לעשות, למה, ואיך (כללו קטעי קוד או תבניות find/replace)
2. ...

### בדיקה
- איך לוודא שהשינוי עובד — אילו בדיקות ב-`tests/` רלוונטיות, ומה לבדוק ידנית בדפדפן

### הערות
- תלויות סדר בין השלבים
- אילוצים, נקודות עדינות, החלטות שהתקבלו
- קבצים שהושפעו אבל לא שונו (ולמה)
```

### 4. הצגה למשתמשת

הציגו תקציר קומפקטי — **לא** את התוכנית המלאה:

```
**תקציר תוכנית סבב N**
- <3-5 נקודות שמכסות את ההחלטות והגישה המרכזיות>

**שאלות פתוחות / פערים שנמצאו:**
- <כל דבר שה-subagent סימן כלא ודאי או לא שלם>

**בדיקת scope:** ~N שלבים — [בגבולות | מתחיל להיות גדול | כדאי לפצל]
```

שאלו את המשתמשת: "משהו לתקן או להוסיף לפני הסבב הבא?"

### 5. איטרציה

אחרי שהמשתמשת מגיבה (או אומרת "תמשיכי" / "נראה טוב"):

הריצו **Plan subagent חדש** במצב ביקורת. תנו לו:
- את התוכנית המלאה הנוכחית
- את המשוב של המשתמשת מהסבב הזה
- הנחיה לבחון את התוכנית בביקורתיות, כמו מפתחת בכירה:
  - **קבצים חסרים** — משהו שדורש שינוי אבל לא רשום?
  - **גישה שגויה** — מודולים ודפוסים נכונים? בדקו מול הקוד האמיתי.
  - **שלבים לא שלמים** — מעורפלים מדי לביצוע בלי ניחוש?
  - **מקרי קצה חסרים** — ולידציה, נתיבי שגיאה, תלויות סדר?
  - **הפניות לא מעודכנות** — נתיבי קבצים/שמות פונקציות באמת קיימים?
  - **בדיקה חסרה** — סעיף הבדיקה מכסה את קריטריוני הקבלה?
  - החילו את המשוב של המשתמשת כתיקונים תוך כדי הביקורת.

ה-subagent מחזיר תוכנית מעודכנת שמשלבת גם את הממצאים שלו וגם את המשוב.

חזרו לשלב 4 עם התוכנית המעודכנת.

### 6. תנאי עצירה

עצרו כשגם וגם מתקיימים:
- ה-Plan subagent לא מצא פערים משמעותיים (רק ניסוח/פורמט קל)
- המשתמשת אומרת שהתוכנית נראית שלמה, או מאשרת במפורש

אם ה-subagent ממשיך למצוא בעיות אחרי 4+ סבבים, ציינו זאת למשתמשת: "אנחנו בסבב N וה-subagent עדיין מוצא פערים — ייתכן שה-scope גדול מדי או שה-issue דורש הבהרה."

### 7. בדיקת scope — פיצול אם צריך

לפני הפרסום, העריכו את ה-scope הסופי. סמנו לפיצול אם **אחד** מהתנאים מתקיים:
- יותר מ-~10 שלבי מימוש משמעותיים
- חלקים שאפשר לשלב בנפרד (למשל תוכן ה-quiz + לוגיקת ה-UI שיכולים להתקדם בנפרד)
- נוגע ב-3+ אזורים שלא חולקים קוד משותף

אם צריך פיצול:

1. אמרו למשתמשת: "התוכנית גדולה מספיק לפיצול. ככה הייתי מחלקת: [פיצול מוצע עם נימוק]."
2. קבלו אישור על הפיצול.
3. צרו issue בן לכל חלק:
```bash
gh issue create --title "<כותרת חלק>" --body "<תיאור חלק, מקשר ל-issue אב #$ARGUMENTS>"
```
4. לכל issue בן, הריצו Plan subagent ממוקד לחלק הזה ופרסמו את התוכנית כתגובה:
```bash
gh issue comment <מספר-issue-בן> --body "<תוכנית>"
gh issue edit <מספר-issue-בן> --add-label "Planned"
```
5. פרסמו תגובת סיכום ב-issue המקורי:
```bash
gh issue comment $ARGUMENTS --body "פוצל ל-issues: #X (חלק 1), #Y (חלק 2). התוכניות פורסמו שם."
gh issue edit $ARGUMENTS --add-label "Planned" --remove-label "Planning"
```

### 8. פרסום התוכנית הסופית (בלי פיצול)

אחרי אישור ובדיקת scope תקינה:

```bash
gh issue comment $ARGUMENTS --body "<תוכנית סופית>"
gh issue edit $ARGUMENTS --remove-label "Planning" --add-label "Planned"
```

פרסמו את התוכנית המדויקת שהמשתמשת אישרה — בלי לשנות פורמט או מבנה.
