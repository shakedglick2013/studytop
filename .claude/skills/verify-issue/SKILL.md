# /verify-issue — בדיקת מימוש מול issue

בדקו האם מה שקיים היום בקוד באמת תואם לתוכנית ולקריטריוני הקבלה של issue — סוג של QA אחרי `/implement-issue`, לפני שסוגרים את ה-issue.

**שימוש:** `/verify-issue 42`

## דרישות מקדימות

קראו את `CONTRIBUTING.md` (דלגו אם כבר נקרא בשיחה הזו).

## הוראות

### 1. הבאת ה-issue, התוכנית ודו"ח המימוש

```bash
gh issue view <number>
gh issue view <number> --comments
```

מתוך התגובות, אתרו:
- תגובה שמתחילה ב-`## תוכנית מימוש` (מ-`/plan-issue`) — זו רשימת השלבים שצריך לבדוק מולה.
- תגובה שמתחילה ב-`## דו"ח מימוש` (מ-`/implement-issue`) — מכילה סטיות ידועות מראש והקשר לבדיקה/דיבוג, שימושי כנקודת פתיחה.

**אם אין תוכנית ואין דו"ח מימוש** — אין מול מה לבדוק. ספרו למשתמשת ועצרו, הציעו להריץ קודם `/plan-issue` ו-`/implement-issue`.

אם יש תוכנית אבל אין דו"ח מימוש — המשיכו בכל זאת (ייתכן שהמימוש בוצע ידנית או מחוץ לזרימת הסקילים), אבל ציינו זאת בדו"ח הסופי.

### 2. תיוג ה-issue

```bash
gh label create "Verifying" --description "" --color "c5def5" 2>/dev/null || true
gh issue edit <number> --add-label "Verifying"
```

### 3. זיהוי וטעינת הקבצים הרלוונטיים

אם יש תוכנית — היא כבר מכילה נתיבי קבצים מדויקים בסעיף "שלבים". קראו את הקבצים האלה **כפי שהם היום**, לא כפי שהתוכנית תיארה אותם.

אם אין תוכנית (רק issue) — זהו את התחום לפי `CONTRIBUTING.md` (`js/pages/`, `js/utils/`, `js/components/` וכו') וחפשו את הקוד הרלוונטי עם Grep/Glob, או Agent מסוג Explore אם ה-scope לא ברור.

### 4. בדיקת התאמה לתוכנית (אם קיימת)

לכל שלב בסעיף "שלבים" של התוכנית, בדקו מול הקוד בפועל:
- **בוצע** — הקוד תואם למה שהשלב תיאר.
- **בוצע אחרת** — משהו נעשה, אבל בגישה/במקום שונה מהמתוכנן. תעדו מה בפועל ולמה זה עדיין סביר (או לא).
- **לא בוצע** — אין זכר לשינוי שהשלב מתאר.

### 5. בדיקת קריטריוני קבלה

לכל שורה בסעיף "קריטריוני קבלה" בגוף ה-issue המקורי, קבעו בפועל (לא לפי מה שהדו"ח טוען שקרה) האם הקריטריון מתקיים:
- קראו את הקוד הרלוונטי, ואם מדובר בהתנהגות נראית-לעין — בדקו ידנית בדפדפן (`python -m http.server` או Live Server).
- סמנו כל קריטריון: מתקיים / לא מתקיים / מתקיים חלקית (עם הסבר קצר מה חסר).

### 6. בדיקת עמידה בסטנדרטים של הפרויקט

עברו על השינויים הרלוונטיים מול הסטנדרטים ב-`CONTRIBUTING.md`:
- RTL תקין במסכים/רכיבים חדשים (חוץ משורת דירוג הכוכבים, שנשארת LTR במכוון).
- בלי תלויות חיצוניות חדשות (npm, CDN, API חיצוני).
- כל גישה ל-`localStorage` עוברת דרך `js/data/storage.js` ומסוננת למשתמש המחובר.
- בלי נתוני דמה מזויפים בברירת מחדל.
- טון תומך ולא שיפוטי בטקסטים למשתמשת.
- הערות קוד חדשות/שנערכו — באנגלית.
- קבצים קטנים ומופרדים לפי תפקיד, לא נערמו שינויים לקובץ ענק אחד.

### 7. בדיקות אוטומטיות וידניות

- אם נוספה או השתנתה פונקציית חישוב, ודאו שיש לה בדיקה תואמת ב-`tests/`, הריצו את דף הבדיקות בדפדפן, וודאו שהיא ירוקה.
- בדקו ידנית בדפדפן את המסך/הרכיב הרלוונטי — כולל RTL ומצב בהיר/כהה אם רלוונטי.
- אם לא ניתן לבצע בדיקה ידנית בדפדפן במסגרת השיחה הנוכחית, ציינו זאת במפורש בדו"ח — אל תטענו שנבדק אם לא נבדק.

### 8. הרכבת הדו"ח

פרסמו תגובה על ה-issue עם `gh issue comment`:

```bash
gh issue comment <number> --body "$(cat <<'EOF'
## דו"ח בדיקת מימוש

### תקציר
<משפט-שניים: האם המימוש תואם לתוכנית ולקריטריוני הקבלה, ברמה גבוהה>

### התאמה לתוכנית
<לכל שלב בתוכנית: ✅ בוצע / ⚠️ בוצע אחרת (הסבר) / ❌ לא בוצע. אם אין תוכנית, כתבו "אין תוכנית זמינה — נבדק מול ה-issue בלבד.">

### קריטריוני קבלה
<לכל קריטריון מה-issue: ✅ מתקיים / ⚠️ חלקית (מה חסר) / ❌ לא מתקיים>

### חריגות מסטנדרטים
<כל סטייה מסטנדרטי הקוד ב-CONTRIBUTING.md שנמצאה. אם אין, כתבו "אין.">

### תוצאות בדיקה
<אילו בדיקות רצו (tests/ ו/או בדיקה ידנית בדפדפן) והתוצאה. אם משהו לא נבדק בפועל, ציינו זאת כאן.>

### המלצה
<Verified — הכל תואם, אפשר לסגור | Needs Fixes — רשימת הפערים שדורשים טיפול לפני סגירה>
EOF
)"
```

### 9. תיוג לפי התוצאה

אם הכל תואם (אין ❌ ואין ⚠️ משמעותיים):

```bash
gh label create "Verified" --description "" --color "0e8a16" 2>/dev/null || true
gh issue edit <number> --remove-label "Verifying" --add-label "Verified"
```

אם נמצאו פערים:

```bash
gh label create "Needs Fixes" --description "" --color "d93f0b" 2>/dev/null || true
gh issue edit <number> --remove-label "Verifying" --add-label "Needs Fixes"
```

### 10. הצגה למשתמשת

הציגו תקציר קומפקטי (לא את הדו"ח המלא) וסיימו בשאלה:

```
**סיכום בדיקת מימוש — issue #<number>**
- <2-4 נקודות: מה נבדק, מה נמצא>

**סטטוס:** Verified | Needs Fixes (<N> פערים)
```

אם נמצאו פערים, שאלו: "לתקן את הפערים עכשיו, או להשאיר לסבב נפרד?" ואל תתחילו לתקן בלי אישור.
